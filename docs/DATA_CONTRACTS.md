# Current agent data contracts

The active application uses the four tables below through `rd/data.py`. Both Athena and local DuckDB must expose the same names. Synthetic files are generated by `scripts/generate_synthetic_data.py`; authorized private files by `scripts/prepare_data.py`.

| Table | Columns |
| --- | --- |
| `returns` | `return_id`, `banner`, `order_number`, `sku`, `style`, `return_order_number`, `channel`, `return_date`, `status`, `refund`, `qty`, `raw_reason`, `store`, `category`, `restocking_fee`, `final_sale`, `aldo_fault` |
| `sku_sales` | `sku`, `lines_sold`, `final_sale_lines` |
| `exchanges` | `confidence`, `exchange_date`, `order_number`, `exchange_sku`, `qty`, `store`, `sales` |
| `baseline` | `category`, `n`, `share` |

`return_id` is a generated integer row key. Recreating real input tables can change IDs if source ordering changes; named real-data scenarios depend on the original prepared snapshot. Amounts are interpreted as CAD by the prototype. Dates use the input calendar without timezone conversion. Nullable numeric values occur in synthetic background records.

Private preparation also keeps `customer_uid` in `returns`. It is intentionally excluded from the tool column allowlist and is absent from synthetic files. Order/return IDs and case traces remain private business information even when customer IDs are omitted.

Categories and thresholds are defined in `rd/detect.py`; the default screen uses 28 days. It compares the **category share among returns**, not a population defect rate. The optional SKU return-rate tool uses a separate sales denominator and is only illustrative because that table lacks dated order lines.

Most evidence tools constrain return dates to `tools.AS_OF.get()`. Known exceptions/limits: `get_return` looks up an ID without a date bound; the precomputed baseline and sales denominator are not point-in-time; the replay date is process-global. These need follow-up work before treating concurrent sessions or chronological backtests as production-safe.

Case and approval JSON shapes live in `rd/store.py`. Tool function signatures and result JSON are kept stable in this reorganization. JSON persistence and approval buttons are a demo, with no authenticated production approver or live retail execution.

The earlier `orders.csv` / cohort contract is archived at `legacy/starter/docs/DATA_CONTRACTS.md`; it does not describe the current four-table agent backend.
